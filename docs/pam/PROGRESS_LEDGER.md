## Lessons
- `redactLaunchProhibitedUserText` is a LAUNCH-COPY word filter (blanks any string containing deposit/withdraw/payout/money/$ to a placeholder) meant ONLY for player-facing points-only text — it is NOT a security sanitiser and must NOT be sprinkled onto back-office compliance data. Applying it to AML/surveillance case titles (verification #23 HIGH) gutted real titles, because case titles inherently name deposits/withdrawals/payouts. The rule: match the sanitiser to the SINK'S TRUST CONTEXT — case titles are internal compliance artifacts (like AML rule names / SAR resolutions, which the AML feature already deliberately leaves un-redacted), rendered as escaped React text, so they need no redaction. Copy-pasting a redaction call because "other admin reads do it" is wrong when the other reads are player-facing and this one isn't. Why it mattered: it silently blanked the primary data on a new compliance endpoint, and no test caught it because every fixture title was benign — always seed a fixture that EXERCISES the sanitiser.
- When rate-limiting or otherwise keying on "the actor," use the SESSION-VALIDATED identity (`httpx.UserIDFromContext`), never `userIDFromRequest` — the latter falls back to the client-supplied `X-User-ID` header, which an attacker can rotate to mint a fresh limiter bucket per request and bypass the throttle (verification #23 MED, reproduced under the dev anon-bypass). A control keyed on attacker-controllable input is not a control.
- Any code that writes untrusted text into an EMAIL HEADER is an SMTP/CRLF header-injection vector unless CR/LF is stripped. `notify.buildMessage` interpolated the rendered Subject + recipients into `Subject:`/`To:` lines with `fmt.Fprintf("...%s\r\n", value)` and no sanitisation; a template subject rendered from admin-supplied `data` (`name:"x\r\nBcc: victim"`) injected real headers under a configured SMTP relay (verification #22 HIGH, `435cead6`). Fix at the BOUNDARY (`sanitizeHeader` in buildMessage) so every caller — GAP-43's send AND the pre-existing resolution-email path — is protected in one place; the body needs no treatment (it's after the header separator and net/smtp dot-stuffs it). Two meta-lessons: (1) a "new feature" (GAP-43) can WIDEN a pre-existing latent flaw (admin `data` → subject) — verifying the whole range since last verification, not just the newest commit, is what surfaced it; (2) render/template output destined for a header or a shell/URL/SQL context must be sanitised for THAT context, not just validated for business rules (validateLaunchFacingReason checked money-wording, not control chars). Why it mattered: silent Bcc exfiltration from a "compliance communication" is exactly the kind of leak an auditor would fail the product on.
- Office (talon-backoffice) UI pages ARE buildable + verifiable autonomously, so the office-UI batch (GAP-35/53/54 + this) does NOT have to wait for GAP-26. - A `date+1day - 1 nanosecond` upper bound is a TRAP against Postgres `timestamptz` (microsecond precision): lib/pq sends the full nanosecond literal `…23:59:59.999999999`, and Postgres ROUNDS it UP to the next day's `00:00:00`. With a `<=` comparator that silently admits a row stamped exactly at next-midnight — an off-by-one that only bites at a day boundary at `.000000` (organic ~1e-6/row, but explicit/backdated inserts hit it). Two different endpoints then disagree on the same period's totals. Use `-1 MICROsecond` (exact in timestamptz(6)) when you must express an exclusive upper bound through a `<=` comparator; or, when you control the comparator, use a half-open `< to+1day`. Verification #20 MED, empirically reproduced + regression-locked (`aeb031d9`). Why it mattered: it made two auditor-facing financial reports return different numbers for the same window — exactly what destroys auditor trust.
